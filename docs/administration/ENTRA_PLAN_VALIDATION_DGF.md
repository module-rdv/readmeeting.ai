# Plan de validation Entra ID et OBO — DGF

## Cadre et état actuel

Ce plan sépare les tests d'intégration locale à jetons synthétiques des validations avec de véritables jetons et appels du tenant DGF. Aucun test réel Entra, OBO ou Graph n'a été exécuté.

Le rapport du Lot 1 consigne **11 tests d'intégration locaux réussis**. Les tests utilisent une clé et des claims synthétiques : ils démontrent la logique de validation locale, pas une émission de jeton ou un consentement DGF. Le code actuel protège `GET /api/v1/security/context`. Le fournisseur OBO est enregistré dans l'API, mais aucun endpoint ne l'appelle ; aucun endpoint Graph backend n'est raccordé.

Les « preuves locales déjà disponibles » ci-dessous sont des références à ces tests et à leur résultat antérieur. Elles ne doivent jamais être présentées comme preuve d'un test réel Entra.

## Critères de clôture

- Les tests positifs et négatifs d'API sont validés avec de véritables tokens du tenant DGF destinés à l'API, en plus des tests locaux synthétiques.
- L'audience, l'issuer, le tenant, le scope et le client appelant observés sont rapprochés des valeurs approuvées. Le claim `ver` est une donnée diagnostique ; le contrôle de version dans le code passe par l'issuer v2 strict, sans vérification distincte du claim `ver`.
- Le test OBO n'est déclaré réussi qu'après un échange serveur réel.
- L'accès Graph n'est déclaré que pour l'opération et la ressource réellement testées.
- Chaque exécution réelle est associée à une référence de preuve non sensible (ticket, rapport, capture expurgée ou compte rendu approuvé).
- Aucune preuve ne contient de token, credential, assertion OBO, clé privée ou contenu transcript.
- Un test bloqué par l'absence de route ou de configuration demeure bloqué ; il n'est pas remplacé par un mock pour conclure à une validation réelle.
